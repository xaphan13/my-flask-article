## 2. Читаемость, модульность, связность

### 2.1 Что сделано хорошо

- **Функции короткие.** Самый длинный обработчик — `account()`, 20 строк. Ни одной
  функции с вложенностью глубже двух уровней.
- **Единообразие маршрутных модулей.** Все четыре начинаются одинаково (импорт логгера,
  затем `flaskblog`), поэтому переход между ними не требует переучивания.
- **Аннотации типов в ключевых местах.** `read_html(name_html: str, name_dir: str) -> str`,
  `art_dict_file: Dict[int, ArticleLang]`, `art: ArticleLang` в обработчике. Покрытие
  неполное, но расставлено там, где помогает.
- **Декоративные баннеры** (`# ====`, `# ---`) визуально режут длинные модули на секции.
  Это осознанная конвенция проекта, зафиксированная в `AGENTS.md`.
- **Русскоязычные UI-строки и комментарии выдержаны последовательно** — смешения языков
  внутри одного слоя нет.

### 2.2 Нарушения связности

**`flaskblog/new_articles/schema_art.py` — три роли в одном модуле (102 строки).**

| Что там лежит | Используется ли |
|---|---|
| `ArticleLang` + загрузка YAML + `art_files` + `art_dict_file` + `read_html`/`render_article` — контракт статей | да, роутами |
| `articles` + `articles_dict` (old version, inline-контент из `arts_content.py`) | нет |
| `UserUpdateBody`, `PostUpdateBody`, `UserPostBase`, `UserSchemaResp`, `PostSchemaResp`, `UserSchemaPostsResp`, `PostSchemaAuthorResp` — DTO для API, которого не существует | нет |

Работающая часть — примерно половина модуля. Имя `schema_art` описывает лишь одну из трёх
ролей, поэтому найти в нём «где читаются файлы статей» неочевидно.

**`flaskblog/logger/config_log.py` — класс и его конфигурация в одном файле.** Словарь
`logging_config` (55 строк) объявлен *после* класса, который на него ссылается. Работает
это только потому, что обращение происходит внутри метода, вызываемого позже. Читателю
приходится прыгать вниз файла, чтобы понять, что делает `settingLogger()`.

### 2.3 Нарушения DRY

| Дубликат | Файлы | Расхождение |
|---|---|---|
| `<head>` страницы | `templates/includes/_head.html` ↔ `templates/new_art/includes/_art_head.html` | второй добавляет CSS highlight.js и динамический `<title>` |
| Подключение скриптов | `templates/includes/_scripts.html` ↔ `templates/new_art/includes/_art_scripts.html` | **highlight.js 11.7.0 против 11.9.0** — рассинхрон версий |
| Шапка навигации | `templates/includes/_header.html` ↔ `templates/new_art/includes/_art_header.html` | второй добавляет `{{ lang }}` в брендинг; список ссылок скопирован дословно, включая обе ветки `if current_user.is_authenticated` |
| Валидаторы уникальности | `RegistrationForm.validate_username/validate_email` ↔ `UpdateAccountForm.…` | во втором добавлено сравнение с текущим значением |
| Инициализация логгера | все 6 модулей, строка `logFC = ConfigLogger.getLogger("FileStdout", "ClientHTTPS")` | идентична; это осознанная конвенция, а не дефект |

Дублирование шаблонных частей — главный риск: две иерархии наследования расходятся
самостоятельно, что уже произошло с версией highlight.js. Правка шапки в одном месте
молча не применится ко второй половине сайта.

### 2.4 Нарушения KISS

- **`multipledispatch` ради перегрузки по арности.** `ConfigLogger.getLogger` объявлен
  дважды (`@dispatch(str)` и `@dispatch(str, str)`). То же достигается параметром со
  значением по умолчанию. Цена: внешняя зависимость, непрозрачность для анализаторов
  (ruff выдаёт `F811 Redefinition of unused getLogger`) и невозможность перейти на
  `@typing.overload` без переписывания.
- **Три декоратора маршрута на `/createDB`** и два неиспользуемых параметра (`post_id`,
  `page`) — следы отладочного эксперимента, оставленные в рабочем коде.
- **Статический класс вместо модуля.** `ConfigLogger` не имеет состояния, кроме флага;
  четыре `@staticmethod` в классе эквивалентны четырём функциям модуля.
- **`import gunicorn` в `flaskblog/run.py`** — импорт ради самого импорта, `gunicorn`
  в коде не используется (`ruff: F401`).

### 2.5 SOLID — где нарушено предметно

| Принцип | Состояние | Конкретика |
|---|---|---|
| SRP | нарушен | `create_app()` собирает приложение **и** дампит весь конфиг в лог; `art_author()` ищет запись, читает файл, мутирует общий объект и рендерит |
| OCP | нарушен | добавление статьи требует правки кода `schema_art.py`, а не данных |
| LSP | не применим | иерархий наследования в Python-коде нет, кроме `db.Model`/`UserMixin` |
| ISP | не применим | интерфейсов/протоколов нет |
| DIP | нарушен | обработчики зависят напрямую от `db.session` и от `open()`; подменить источник данных в тесте нечем |

Для небольшого приложения это приемлемый компромисс, а не приговор. Существенно здесь одно: нарушение
DIP — прямая причина нетестируемости (см. §3).

Прочие отклонения от идиом Python/Flask:

- **Переопределённый `User.__init__`** в `flaskblog/models.py` с пустыми строками по

- **Классический стиль `db.Column`** вместо `Mapped[]`/`mapped_column` из SQLAlchemy 2.0.
  Работает, но лишает проект статической типизации моделей.
- **Смешение регистров имён**: модули в camelCase, функции — `snake_case`, методы

`ruff` и `black` настроены в `pyproject.toml`, но не установлены в окружении
(`ruff: команда не найдена` в `.venv`) — то есть линтер фактически не является частью
рабочего процесса.

## 3. Тестируемость — главный технический долг

Тестов нет ни одного. Существеннее, что код к ним ещё и не готов:

1. **Побочные эффекты на импорте.** `import flaskblog` создаёт каталог логов, открывает
   файл лога и настраивает `dictConfig` глобально. Тестовый прогон не может это обойти.
2. **Конфигурация фиксируется до вызова фабрики.** Атрибуты `Config` вычисляются при
   импорте `flaskblog.config`, поэтому `monkeypatch.setenv` не действует. Тестовый
   конфиг придётся передавать через `config_class=`, минуя окружение.
3. **Зависимость от cwd.** Каталог статей вычислен в значении по умолчанию `read_html`
   один раз при импорте — запуск pytest из другого каталога ломает чтение статей, и
   `chdir` в фикстуре не помогает.
4. **Нет точки внедрения зависимостей.** Чтобы протестировать `art_author` без диска,
   нужно патчить `read_html` в пространстве имён модуля маршрутов.
5. **Разделяемое мутируемое состояние.** `art_dict_file` — общий словарь; тест, изменивший
   `art.content`, повлияет на следующий тест в том же процессе.

Барьер входа при этом низкий: `create_app(config_class=...)` уже параметризован, а
`app.test_client()` работает — я использовал его для проверки маршрутов при подготовке
этой документации.

## 4. Дефекты по степени критичности

### 4.1 Блокирующие

**B1. `SECRET_KEY` и пароль БД пишутся в лог открытым текстом.**
`flaskblog/__init__.py`, строка 26:

```python
logFC.info("'create_app 5' app.config:\n" + "\n".join(f"    {k} = {app.config[k]!r}" for k in sorted(app.config)))
```

Проверено запуском — в выводе присутствуют `SECRET_KEY`, `DB_PASSWORD`, `DB_USER`
в открытом виде. Логгер `FileStdout` пишет и в файл, и в stdout, поэтому секреты
попадают одновременно в `{LOG_DIR}/{LOG_FILE}` (в Docker он смонтирован на хост)
и в журнал контейнера. Компрометация `SECRET_KEY` = возможность подделать cookie сессии
и войти под любым пользователем.

**B2. Docker-контур приложения не стартует: в `dock_flask.env` нет `DATABASE_URI`.**
Проверено: `grep -c DATABASE_URI flaskblog/dock_flask.env` → `0`. Сборка DSN из `DB_*`
в `flaskblog/config.py` закомментирована, значит `SQLALCHEMY_DATABASE_URI` окажется `None`,
и `db.init_app(app)` упадёт с
`RuntimeError: Either 'SQLALCHEMY_DATABASE_URI' or 'SQLALCHEMY_BINDS' must be set.`
(воспроизведено отдельным запуском). Оговорка: `dock_flask.env` не в git, поэтому у другого
разработчика он может отличаться — но текущий экземпляр в рабочем дереве неработоспособен.

**B3. `/createDB` выполняет DDL без авторизации, по GET.**
`flaskblog/main/routesMain.py`. Любой анонимный посетитель вызывает `db.create_all()`.
В текущей схеме прямого разрушения данных нет (`create_all` не удаляет существующие
таблицы), но это неаутентифицированная точка воздействия на схему и удобный вектор
для нагрузочного злоупотребления. GET-метод к тому же делает вызов доступным через
`<img src>` с чужого сайта.

**B4. `debug_mode=True` захардкожен в точке входа.**
`flaskblog/run.py`, строка 6: `app = create_app(debug_mode=True)`. Эту же точку входа
использует Docker: `gunicorn --bind 0.0.0.0:5000 flaskblog.run:app`. Проверенное
следствие: `PROPAGATE_EXCEPTIONS` включается, обработчик `errors/500.html`
**не вызывается**, клиент получает заглушку WSGI-сервера, а трейсбек уходит в stdout
вместо настроенного логгера. Интерактивного отладчика Werkzeug не возникает
(проверено curl-запросом), поэтому утечки исходников в HTTP-ответе нет — но
эксплуатационное поведение всё равно неверное.

### 4.2 Высокая критичность

**H1. Open redirect в `login`.** `next_page = request.args.get('next')` подставляется
в `redirect()` без проверки. Ссылка `/login?next=https://evil.example` после успешного
входа уводит пользователя на внешний домен — классический вектор фишинга. Нужна проверка,
что URL относительный (`urlparse(next).netloc == ''`).

**H2. `logout` доступен по GET без CSRF-защиты.** Сторонний сайт разлогинивает
пользователя тегом `<img src="https://site/logout">`. Ущерб ограничен (отказ в
обслуживании уровня UX), но исправляется тривиально — методом POST с CSRF-токеном.

**H3. Ни одного `try/except` в прикладном коде.** Проверено поиском по всем `.py`:
конструкций `try`, `except`, `rollback` нет вообще. Следствия: `IntegrityError` при гонке
регистраций (см. H4) оставляет сессию SQLAlchemy сломанной; `FileNotFoundError` при
отсутствующем файле статьи, `OSError` при недоступном диске, `OperationalError` при
недоступной БД — все превращаются в 500 без диагностики.

**H4. TOCTOU при регистрации.** Уникальность проверяется валидатором формы
(`SELECT`), а обеспечивается ограничением БД (`unique=True`). Два одновременных
запроса с одним e-mail проходят валидацию и сталкиваются на `commit()`, где
`IntegrityError` не перехвачен → 500 вместо внятного сообщения.

**H5. Нет ограничения размера загружаемого файла.** Проверено: `MAX_CONTENT_LENGTH`
в конфиге равен `None`, а nginx разрешает `client_max_body_size 1000M`. Обработчик
`save_picture` синхронно открывает файл через Pillow в рабочем процессе. Большое
изображение или декомпрессионная бомба (маленький файл, разжимающийся в гигабайты)
исчерпает память воркера. Усугубляется тем, что воркер всего один.

**H6. Тип загружаемого файла проверяется только по имени.**
`FileAllowed(['jpg','png'])` и `os.path.splitext(form_picture.filename)` смотрят на
строку, присланную клиентом; `Image.verify()` не вызывается (проверено поиском).
Единственная фактическая защита — то, что Pillow не сможет открыть не-изображение.
Записать исполняемый файл в `static/` таким образом не удастся (расширение берётся из
исходного имени, но Pillow сохраняет по формату), однако проверку следует сделать явной.

**H7. Нет валидации пароля.** `RegistrationForm.password` имеет единственный валидатор
`DataRequired()` — принимается пароль из одного символа. Ни минимальной длины,
ни ограничения сверху (для bcrypt важен предел 72 байта), ни проверки сложности.

### 4.3 Средняя критичность

**M1. Ошибки предметной области отображаются в неверные HTTP-коды.** `art_dict_file[art_id]`
даёт `KeyError` → 500 вместо 404 (проверено на `/art/Max/999`). Правильно —
`art_dict_file.get(art_id)` и `abort(404)`; функция `abort` в проекте не используется ни разу.

**M2. Параметр `<author>` в маршруте декоративен.** `/art/anybody-else/1` возвращает
статью автора Max с кодом 200 (проверено). URL допускает бесконечное число вариантов,
ведущих на один документ, — плохо для SEO (дубли) и вводит в заблуждение.

**M3. Мутация разделяемого объекта в обработчике.** `art.content = content` изменяет
модуль-level экземпляр `ArticleLang`, общий для всех запросов и потоков. Сейчас
безвредно (пишется одно и то же), но это заложенная гонка: любое запросо-зависимое
поле немедленно станет источником межзапросной утечки данных.

**M4. Cookie сессии без флагов безопасности.** Проверено: `SESSION_COOKIE_SECURE=False`,
`SESSION_COOKIE_SAMESITE=None` (значения по умолчанию Flask; в `Config` они не заданы).
При работе через TLS-прокси cookie всё равно может уйти по HTTP, а `SameSite` не
ограничивает межсайтовую отправку.

**M5. Отсутствует `ProxyFix`.** За nginx `request.remote_addr` равен адресу прокси, а
не клиента: `X-Forwarded-For` приходит, но не учитывается. Любой будущий rate limiting
или аудит по IP окажется бесполезным.

**M6. Старые аватары не удаляются.** `save_picture` записывает новый файл и обновляет
`User.image_file`, прежний остаётся на диске навсегда. Каталог `static/profile_pics/`
растёт неограниченно и при этом **не смонтирован в volume** — в Docker файлы исчезают
при пересборке образа, то есть данные и теряются, и накапливаются одновременно.

**M7. Логирование в горячем пути.** `read_html` пишет INFO-строку с полным путём на
каждое чтение файла, `art_home` логирует весь индекс статей. Это дополнительный
синхронный ввод-вывод на каждый запрос плюс быстрое исчерпание 21 МБ ротации.

**M8. PII в логах.** При регистрации в лог попадает `__repr__` пользователя с e-mail.

**M9. Нет `Image.close()`.** `save_picture` не закрывает объект Pillow и не использует
контекстный менеджер — дескриптор освободится только сборщиком мусора. При потоке
загрузок это накопление открытых дескрипторов.

## 5. Надёжность инфраструктуры

| Проблема | Где | Следствие |
|---|---|---|
| `depends_on: nginx` вместо `db` | `compose-nginx-db.yml`, сервис `app_flask` | порядок старта относительно БД не определён; первый запрос после холодного старта может упасть |
| Нет `healthcheck` ни у одного сервиса | там же | Docker считает контейнер живым, даже если приложение внутри упало; `restart: always` перезапустит только при выходе процесса |
| Нет retry подключения к БД | `flaskblog/__init__.py` | недоступная на старте БД = ошибка на первом запросе, без ожидания готовности |
| `version: "3.7"` | `compose-nginx-db.yml` | ключ устарел и игнорируется Compose v2 |
| Один воркер gunicorn | `command` сервиса `app_flask` | пропускная способность = 1 запрос одновременно; ресайз аватара блокирует весь сайт |
| Контейнер работает под `root` | `flaskblog/DockerFlask` | нет `USER`, эскалация при компрометации процесса |
| Нет graceful shutdown | весь проект | обработчиков сигналов нет; полагается на поведение WSGI-сервера |
| Аватары вне volume | `compose-nginx-db.yml` | пользовательские файлы теряются при пересборке |
| Нет `.env.example` | корень | воспроизвести окружение можно только по документации; все три `*.env` gitignored |
| Нет CI | отсутствует `.github/` | ни линтера, ни сборки, ни проверок на PR |
