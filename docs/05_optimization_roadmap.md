## 1. Порядок работ

Последовательность выбрана так, чтобы каждый следующий шаг опирался на защиту,
созданную предыдущим.

|---|---|---|
| 0 | P0-безопасность: B1, B4, B3, H1, H2 | утечка `SECRET_KEY` и DDL без авторизации делают бессмысленным любое другое улучшение |

## 2. Архитектурные улучшения

### 2.1 Развивать YAML-манифест статей (P2)

Сейчас метаданные статей вынесены в `flaskblog/new_articles/articles.yaml`, а
`art_files` и `art_dict_file` строятся из YAML при импорте. Добавление статьи требует
изменения YAML, добавления файла `.html`/`.md`/`.markdown` и перезапуска процесса.
Контент уже отделён от Python-кода; дальнейшее улучшение — автоматическая перезагрузка
манифеста или управляемый редактор.

`ArticleLang` уже выполняет валидацию данных манифеста при импорте. Следующий шаг имеет
смысл только при необходимости обновлять статьи без перезапуска: загрузчик может проверять
`mtime` YAML и файлов контента и атомарно перестраивать словарь. Переносить метаданные в
другой JSON-манифест не требуется.

### 2.2 Ввести тонкий слой доступа к статьям (P1)

Создать `flaskblog/new_articles/repository.py` с единственной ответственностью — выдавать
статьи:

```python
def list_articles() -> list[ArticleMeta]: ...
def get_article(art_id: int) -> Article | None: ...   # None вместо KeyError
```

Что это даёт сразу: исчезает M1 (обработчик получает `None` и вызывает `abort(404)`),
появляется точка внедрения зависимости для тестов (§3 в [04](04_code_quality.md), пункт 4),
и кэш из §3.1 ставится в одном месте, а не размазывается по обработчику.

Полноценный сервисный слой для контура пользователей на 723 строках не нужен — там
достаточно локальных исправлений.

### 2.3 Устранить cwd-зависимость (P0, тривиально)

`get_path_dir()` строит путь от `os.getcwd()`, а результат фиксируется в значении по
умолчанию `read_html`. Замена на путь от `__file__` убирает целый класс отказов
(запуск из другого каталога, cron, systemd, pytest):

```python
ARTICLES_DIR = Path(__file__).resolve().parent.parent / "templates" / "content_art"
```

Аргумент `name_dir` при этом стоит оставить параметром без вычисляемого дефолта, чтобы
значение не замораживалось на импорте.

### 2.4 Разделить конфигурацию по средам (P1)

Один класс `Config` обслуживает все среды, а режим отладки приходит отдельным аргументом
`debug_mode` — отсюда B4. Ввести `BaseConfig` / `DevConfig` / `ProdConfig` / `TestConfig`,
где `DEBUG` — свойство класса, а не параметр фабрики. Дополнительно:

- обязательные переменные проверять при старте и падать с внятным сообщением, а не
  с `RuntimeError` из глубины Flask-SQLAlchemy (B2);
- `TestConfig` с `SQLALCHEMY_DATABASE_URI = "sqlite:///:memory:"` и `WTF_CSRF_ENABLED = False`
  — это предпосылка для §5.1;
- задать `SESSION_COOKIE_SECURE`, `SESSION_COOKIE_SAMESITE="Lax"`,
  `MAX_CONTENT_LENGTH` (M4, H5).

### 2.5 Подготовка к масштабированию и асинхронным нагрузкам (P2)

Приложение почти stateless, поэтому горизонтальное масштабирование дёшево — мешают три
вещи, и все устранимы:

| Препятствие | Решение |
|---|---|
| Аватары на локальном диске воркера (M6) | вынести в volume, а при нескольких инстансах — в объектное хранилище (S3/MinIO) либо на общий том |
| Синхронный ресайз изображения в воркере | при росте нагрузки — вынести в очередь задач; на текущем масштабе достаточно `MAX_CONTENT_LENGTH` + несколько воркеров |
| Один воркер gunicorn | `-w $((2*CPU+1))` и `--timeout`; после этого разделяемое состояние из §2.1 становится критичным, поэтому порядок работ важен |

**Про асинхронность отдельно.** Переход на `async def` в текущем виде выгоды не даст:
Flask с ASGI-адаптером не сделает синхронные `psycopg2` и `open()` неблокирующими,
а Flask-SQLAlchemy и Flask-Login синхронны. Если асинхронность потребуется, правильный
маршрут — не переписывать этот проект на `async`, а увеличить число синхронных воркеров;
это тот же выигрыш при кратно меньшем риске. Полноценный async-стек (FastAPI + SQLAlchemy
2.0 async + `aiofiles`) оправдан только при появлении реальных внешних I/O-вызовов, которых
в проекте пока нет.

Сессии в подписанных cookie позволяют масштабироваться без внешнего session-store — но
только пока `SECRET_KEY` одинаков во всех инстансах и не утёк (B1).

### 2.6 Отказоустойчивость (P1)

- `healthcheck` для всех четырёх сервисов compose; для `app_flask` — отдельный endpoint
  `/healthz`, который проверяет доступность БД и не пишет в лог.
- `depends_on: db` с `condition: service_healthy` вместо текущего `depends_on: nginx`.
- Убрать `version: "3.7"` (L-уровень, но делается вместе).
- `USER` без привилегий в `flaskblog/DockerFlask`.
- Обработчик `SIGTERM` не требуется: gunicorn сам завершает воркеры корректно, достаточно
  задать `--graceful-timeout`.

## 3. Оптимизация производительности

Замеров не проводилось (см. [04](04_code_quality.md) §6), поэтому ниже — оценки по
структуре кода, отсортированные по соотношению выигрыша к трудозатратам.

### 3.1 Кэшировать тела статей (P1, наибольший эффект)

Сейчас каждый показ статьи — это `open()` + полное чтение файла + запись INFO-строки в лог
(M7). Кэширования нет ни на одном уровне ([02](02_architecture.md) §4.2).

Поскольку файлы меняются только при деплое, достаточно кэша в памяти процесса с проверкой
`mtime`, без Redis:

```python
@lru_cache(maxsize=64)
def _read_cached(path: Path, mtime_ns: int) -> str: ...   # mtime в ключе = авто-инвалидация
```

Это убирает дисковый ввод-вывод из горячего пути. Одновременно снизить логирование
`read_html` до `DEBUG` — иначе выигрыш съест синхронная запись в лог; для Markdown
отдельно кэшировать стоит и результат `markdown()`.

### 3.2 Отдавать статику и кэш-заголовки через nginx (P2)

`nginx/nginx.conf` проксирует в приложение абсолютно всё, включая `/static/*`. Добавить
`location /static/` с `alias`, `expires` и `gzip` — CSS/JS/картинки перестанут занимать
воркеры Python. Для HTML статей уместны `Cache-Control` и `ETag`: контент почти
неизменяемый, а условные запросы уберут повторную передачу тела.

### 3.3 Устранить N+1 до его появления (P2)

Сейчас `User.posts` объявлен как `lazy=True`, а `Post` не используется ни одним
маршрутом — проблемы нет. Но первая же страница со списком постов и обращением к
`post.author` даст N+1. При реализации CRUD постов сразу использовать
`db.session.execute(select(Post).options(joinedload(Post.author)))`.

### 3.4 Индексы и запросы (P2)

`username` и `email` имеют `unique=True`, что создаёт индекс, — поиск при логине
эффективен. Добавить индекс на `Post.user_id` (внешний ключ, по нему пойдут выборки
постов автора) и на `Post.date_posted` (сортировка ленты) — до наполнения таблицы это
бесплатно.

### 3.5 Логирование (P1)

Сообщения формируются f-строками до проверки уровня, а логгер `FileStdout` пишет
одновременно в файл и stdout. Дёшево и заметно:

- перевести диагностику горячего пути на `DEBUG`, уровень задавать переменной `LOG_LEVEL`;
- убрать дамп конфигурации из `create_app` (он же B1);
- в Docker оставить только stdout, а сбор логов доверить драйверу Docker — двойная
  запись не нужна.

### 4.2 Внедрить миграции (P1)

Миграций нет, `db.create_all()` не изменяет существующие таблицы — любая правка
`models.py` сейчас требует ручного пересоздания БД. Добавить `Flask-Migrate`:

```bash
flask db init && flask db migrate -m "baseline" && flask db upgrade
```

Это делает пункт 3 из §4.1 законченным: `/createDB` удаляется, а схема управляется
явными версионированными скриптами. Сделать до того, как в БД появятся реальные данные.

### 4.3 Удалить мёртвый код (P2, механическая работа)

L1-L6, суммарно ≈ 21 % Python-кода: `data_ex.py`, `loggerSettings.json`,
`articles`/`articles_dict` + `arts_content.py`, 7 неиспользуемых DTO,
`templates/errors/new.html`. Отдельно решить судьбу `Post` (L6): либо реализовать CRUD,
либо удалить модель — «объявлено, но не используется» вводит в заблуждение и раздувает
контекст для AI-агентов.

Также вычистить `docker_manager.sh` (L11: личные пути `$HOME/222/…`, контейнеры
`redis_new`/`pgadmin_new`) и поправить `git_manager.sh` (L12: ветка `two_app`).

### 4.4 Устранить дублирование шаблонов (P2)

Две иерархии наследования уже расползлись (L13). Свести к одной базе с блоками:

```
base.html                       ← общие head/header/footer/scripts + {% block %}
├── layout.html                 ← + flash-сообщения
└── new_art/art_base.html       ← + сайдбар, highlight.js
```

Это устраняет три пары дубликатов из §2.3 в [04](04_code_quality.md) и попутно решает
проблему невидимых flash-сообщений на страницах статей.

## 5. Developer Experience

### 5.1 Тесты — первый по важности пункт всего документа (P1)

Тестов нет, и это блокирует безопасный рефакторинг. Начинать следует не с покрытия,
а с каркаса:

```
pyproject.toml           [dependency-groups] dev = ["pytest", "pytest-cov", "ruff", "black"]
tests/conftest.py        фикстуры app (TestConfig, in-memory SQLite) и client
tests/test_routes.py     smoke: коды ответов всех 12 маршрутов
tests/test_articles.py   art_home, art_author, поведение при неизвестном art_id
tests/test_auth.py       регистрация → вход → доступ к /account → выход
```

Первый же smoke-тест закрепляет уже проверенные факты и не даст им регрессировать:

```python
def test_unknown_article_returns_404(client):     # сейчас упадёт: возвращается 500 (M1)
    assert client.get("/art/Max/999").status_code == 404
```

Предпосылки уже есть: `create_app(config_class=...)` параметризован, `app.test_client()`
работает — при подготовке этой документации карта маршрутов и коды ответов получены
именно так. Мешают три вещи из §3 в [04](04_code_quality.md): побочные эффекты на импорте,
конфиг, фиксируемый до вызова фабрики, и cwd-зависимость (§2.3 выше).

Разумная первая цель — smoke-покрытие всех маршрутов плюс тесты на исправляемые дефекты
(H1, H4, M1). Гнаться за процентом покрытия на этом этапе не нужно.

### 5.2 Линтеры в рабочий процесс (P1)

`ruff` и `black` настроены в `pyproject.toml`, но не установлены в `.venv` — линтер
фактически не запускается. Добавить их в dev-группу и подключить `pre-commit`.

Про 31 замечание `ruff`: `I001` (16 штук) автоисправлением **починить нельзя** — сортировка
импортов сломает обязательный порядок «логгер до всего», на котором держится инициализация.
Правильный шаг — либо явно исключить `I001` для маршрутных модулей, либо убрать саму
зависимость от порядка импортов (тогда правило начнёт работать честно). `N999` (camelCase
в именах модулей) требует переименования файлов — это ломающее изменение путей импорта,
поэтому делать его стоит одним коммитом вместе с §4.1.

### 5.3 CI (P1)

Каталога `.github` нет. Минимальный пайплайн на push/PR: `uv sync` → `ruff check` →
`ruff format --check` → `pytest`. Отдельная задача — сборка Docker-образа, что заодно
поймает дефекты класса B2 (несогласованность `dock_flask.env` и кода) до развёртывания.

### 5.4 Локальный запуск (P2)

Основной барьер — три gitignored `*.env` без примеров: воспроизвести окружение можно
только по [setup-and-run.md](setup-and-run.md). Что добавить:

- `local.env.example`, `.env.example`, `dock_flask.env.example` с безопасными
  значениями-заглушками и комментариями;
- `Makefile` (или `justfile`) с целями `install`, `run`, `lint`, `test`, `up`, `down` —
  это же зафиксирует правило «запускать только `python -m flaskblog.run`», на котором
  сейчас легко ошибиться;
- проверку обязательных переменных при старте (§2.4) — она превращает загадочные
  `TypeError` на импорте и `RuntimeError` из Flask-SQLAlchemy в понятное сообщение.

### 5.5 Наблюдаемость (P2)

Логи есть, но связать записи одного запроса нечем ([03](03_execution_flow.md) §5.3).
Дёшево и полезно: `before_request` с генерацией request-id и `after_request` с записью
метода, пути, кода и длительности; `X-Forwarded-For` через `ProxyFix` (M5), чтобы
в логах был реальный IP клиента. Метрики Prometheus и трассировка на текущем масштабе
преждевременны.
